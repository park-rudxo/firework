# firework

**SSAFY 프로젝트 공유 플랫폼 — 프로젝트판 플레이스토어.**

SSAFY에서는 관통·특화·자율 프로젝트에 토이 프로젝트까지 끊임없이 만들어지는데, 공유는 노션·카톡·에타에 흩어지고 만든 사람이 "실제로 써본 사람"의 솔직한 피드백을 받을 창구는 없다. firework는 그 흐름을 한 줄로 잇는다.

```
둘러본다 → 써본다 → 구독한다 → 버그를 제보한다 → 만든 팀이 고친 소식을 받는다
```

한 번 써보고 끝나는 곳이 아니라, 만든 팀이 계속 관리하고 쓰는 사람이 따라갈 수 있는 곳을 목표로 한다. 익명 설문과 경품 추첨은 그 위에 얹은 도구이지 서비스의 중심이 아니다.

---

## 이 서비스의 핵심 결정

### 1. 설문 응답은 작성자 정보 없이 전달된다 — 스키마 수준에서

익명 설문과 "응답자 대상 추첨"은 정면으로 충돌한다. 익명인데 당첨자를 어떻게 뽑나?

**테이블을 둘로 쪼개고 서로 참조하지 않는 것**으로 푼다.

| 테이블 | 담는 것 | 담지 않는 것 |
| --- | --- | --- |
| `survey_response` | 응답 내용뿐 | **userId**, **시간 정보 일체** (둘 다 컬럼 자체가 없음) |
| `survey_participation` | 누가 응답했는지, 시각 | 응답 내용 |

두 레코드는 한 트랜잭션에서 생기지만 서로를 가리키는 컬럼이 없다. 그래서:

- 제작자는 응답 내용만 본다. 제작자 화면 어디에도 둘을 잇는 조회가 없다
- `survey_response.id`는 순번이 아니라 UUID라 제출 순서를 추론할 수 없다
- **응답에 시간 정보를 아예 두지 않는다.** 처음에는 "시각은 위험하니 날짜만"으로 뒀는데 그걸로는 부족했다. 하루 응답이 한 건뿐인 날이면 그 날짜만으로 `participation.createdAt`과 1:1로 붙는다. 사용자가 적은 서비스에서는 그런 날이 오히려 흔하다. 기간별 집계가 필요한 홈의 "이번 주 인기"는 개인과 무관한 합계 카운터(`project_stat_daily.surveyResponses`)를 쓴다
- **개별 응답은 3건 단위 묶음으로만 공개한다.** 임계만 두고 그 위로 전부 보여주면, 제작자가 결과 화면을 열어둔 채 기다리다 3건에서 4건이 되는 순간 "방금 늘어난 하나"를 지목할 수 있다. 그러면 그 한 건은 방금 부탁했던 사람의 것으로 좁혀진다. 그래서 3, 6, 9…처럼 묶음으로만 늘린다

**약속의 크기를 정확히 적어둔다.** 이 구조가 지키는 것은 *제작자에게 작성자 정보를 제공하지 않는다*이지, *누구도 절대 알아낼 수 없다*가 아니다. 응답자가 한 명뿐이면 두 표를 나란히 놓기만 해도 대응이 보이고, DB에 직접 접근할 수 있는 운영자는 여전히 추론할 수 있다. 표본이 작을 때 익명성을 깨는 것은 구조가 아니라 사람 수다. 참이 아닌 것을 약속하면 그 약속을 믿고 솔직하게 쓴 사람이 다치므로, 화면에도 한계를 함께 적는다(`/about/anonymity`).

### 2. 추첨은 사후 검증할 수 있다 — commit–reveal

제작자가 직접 추첨을 돌리니 "지인한테 몰아준 거 아니냐"는 의심이 필연이다.

1. **개설 시** 서버가 `seed`를 만들고 `sha256(seed)`만 공개한다 (커밋)
2. **추첨 시** `HMAC-SHA256(seed, ticketCode)` 값을 정렬해 상위 N명을 뽑는다
3. **추첨 후** `seed`를 공개한다 (리빌)

누구나 `sha256(seed) == seedHash`를 확인하고 당첨자를 처음부터 재계산할 수 있다. 추첨 공개 페이지에 응모 티켓 목록과 검증 방법이 그대로 노출된다.

### 3. 구독과 알림은 다른 것이다

유튜브에 구독 버튼과 종 버튼이 따로 있는 이유와 같다. **구독은 사이트 안의 일이고, 알림 동의는 밖으로 메시지를 내보내도 좋다는 허락이다.** 하나로 합치면 "관심은 있는데 알림은 싫다"를 표현할 방법이 없어진다.

- **구독**(`project_follow`) — 관심 목록과 캘린더에 들어온다. 이것만으로는 어떤 메시지도 나가지 않는다.
- **알림 동의**(`project_notification_pref`) — 주제별로 따로 켠다. **기본은 전부 꺼짐이다.**
- **구독을 끊으면 동의도 함께 지운다.** 남겨두면 다시 구독한 순간 예전 동의가 되살아나, 사용자가 껐던 조작이 무효가 된다.

동의를 불리언 컬럼이 아니라 **행의 존재**로 표현한 것도 같은 이유다. 불리언에 기본값을 주면 나중에 기본값을 `true`로 바꾸는 한 줄로 전원에게 메시지가 나가버린다. 행이 없으면 꺼진 것이고, 그 기본값을 뒤집을 방법이 없다.

주제는 둘뿐이다. 늘리기는 쉽고 줄이기는 어렵다.

| 주제 | 무엇이 오나 |
| --- | --- |
| `UPDATE` | 진행 소식, 새 버전, 정식 출시 |
| `RECRUITING` | 베타 테스트 모집, 설문 개설 |

### 4. 알림은 "무엇을 알리지 않는가"가 핵심이다

설문에 새 응답이 들어올 때마다 제작자에게 알리면, 제작자는 **응답이 도착한 시각을 알게 된다.** 응답 행에서 시간 정보를 지워둔 의미가 그 알림 하나로 되살아난다 — "방금 A한테 써달라고 부탁했는데 5분 뒤 알림이 왔다"는 추론이 성립한다.

그래서 개별 응답 알림은 만들지 않는다. 응답이 3건에 도달해 개별 피드백을 볼 수 있게 된 순간에만 한 번 알린다.

알림이 가는 곳은 이렇다. 사이트 알림은 구독자 전원에게 가고, 밖으로 나가는 메시지는 그 주제를 직접 켠 사람에게만 간다.

| 알림 | 받는 사람 | 밖으로도 나가나 |
| --- | --- | --- |
| 진행 소식 게시 | 구독자 | `UPDATE`를 켠 사람만 |
| 테스터 모집 · 설문 개설 | 구독자 | `RECRUITING`을 켠 사람만 |
| 버그 제보 접수 | 프로젝트 관리 팀 전원 | 본인이 수신을 켰다면 |
| 제보 처리 상태 변경 | 제보자 | **제보자가 그 제보에 알림을 켰을 때만** |
| 추첨 당첨 | 당첨자 (없으면 당첨 사실을 영영 모른다) | — |
| 당첨자가 연락처 제출 | 제작자 | — |
| 설문 응답 3건 도달 | 제작자 | — |
| 신고 접수 | 관리자 (`CRITICAL`은 제목부터 다르게) | — |
| 링크 깨짐 제보 | 제작자에게만 (관리자 큐를 거치지 않음) | — |
| 숨김·삭제 조치 | 해당 프로젝트 제작자 (사유 포함) | — |

### 5. Mattermost는 인증과 수신을 분리한다

싸피 교육생은 Mattermost를 매일 쓴다. 사이트에 매일 들어오지 않아도 관심 있는 프로젝트에 변화가 생겼을 때 돌아올 수 있는 통로다.

계정 연결이 두 가지를 해주지만 **끝까지 분리해서 다룬다.**

1. **인증** — 서버가 OAuth 토큰으로 직접 `/users/me`를 불러 확인한 `mattermostUserId`. 싸피가 이미 확인한 계정이므로, 닉네임에 직접 적어내는 소속보다 확실한 신원 근거다. 한 Mattermost 계정은 한 firework 계정에만 붙는다(다중 계정 차단).
2. **수신** — 사용자가 자기 계정에서 만든 개인 Incoming Webhook. 전역 스위치는 **기본 꺼짐**이고, 프로젝트별 동의까지 있어야 한 통이 나간다.

인증하려고 연결했을 뿐인 사람에게 메시지가 가기 시작하면 안 되므로, 연결이 수신을 자동으로 켜지 않는다.

**발송 직전에 동의를 한 번 더 확인한다.** 큐에 넣는 시점과 보내는 시점 사이에 사람은 구독을 끊고, 알림을 끄고, 연결을 해제한다. 넣을 때 확인한 것으로 충분하다고 보면 그 취소들이 전부 무시된다. 확인이 어긋나면 실패가 아니라 `CANCELLED`로 닫는다 — 재시도할 이유가 없기 때문이다.

웹훅 주소는 그 자체가 "이 사람에게 메시지를 보낼 수 있는 권한"이라 AES-256-GCM으로 봉해 저장하고(`src/lib/secret-box.ts`), 등록 시 호스트를 `MATTERMOST_URL`로 못박고 경로를 `/hooks/`로 제한한다(임의 주소를 넣어 우리 서버가 내부망을 때리게 만드는 것을 막는다).

> 배포 전 확인할 것: 싸피 Mattermost가 OAuth 애플리케이션 등록을 허용하는지. `MATTERMOST_*`가 비어 있으면 연결 버튼 자체를 띄우지 않고, 인증이나 발송이 된 것처럼도 표시하지 않는다.

### 6. 버그 제보는 신고와 다른 큐다

신고(`report`)는 "이 프로젝트에 문제가 있으니 운영자가 봐야 한다"이고, 제보(`bug_report`)는 "잘 쓰다가 이게 안 되더라"다. 받는 사람도 관리자가 아니라 제작자이고, 결말도 숨김·삭제가 아니라 수정이다. 그래서 큐를 섞지 않는다.

제보는 상시 열려 있다. 제작자가 설문을 열어줘야만 피드백을 낼 수 있으면 그동안 막힌 곳을 전할 방법이 없다.

`접수 → 확인 중 → 수정 완료`(또는 `고치지 않음`·`중복`). 제보자는 알림을 켜지 않아도 프로젝트 페이지에서 진행을 볼 수 있다. 소식을 올릴 때 제보를 함께 고르면 수정 완료로 닫히고, "제보가 실제 개선으로 이어졌다"가 화면에서 이어진다.

본문에는 재현 경로와 계정 상태가 섞이기 쉬워서(`로그인하고 마이페이지 들어가면…`) **제보자와 프로젝트 관리 팀만** 본다. 공개 화면에는 건수와 상태만 나온다.

### 7. 프로젝트는 팀의 것이다

`project_member`에 `OWNER`/`MAINTAINER`/`CONTRIBUTOR`를 만들어두고 판정은 `ownerId`로만 하면, 공동 관리자로 초대받은 사람이 할 수 있는 일이 하나도 없다. 팀이 만든 프로젝트를 모으는 서비스에서 그건 그냥 고장이다.

권한 판정은 전부 `src/features/project/permissions.ts`를 지난다.

| 역할 | 할 수 있는 것 |
| --- | --- |
| `OWNER` | 전부. 공개·비공개 전환처럼 되돌리기 어려운 것도 |
| `MAINTAINER` | 내용 수정, 소식 게시, 제보 처리, 설문·일정 운영 |
| `CONTRIBUTOR` | 팀원으로 이름만 올라간다 |

### 8. 신고에 자동 숨김은 없다

신고 N건으로 프로젝트가 자동으로 내려간다면 경쟁 프로젝트를 신고 몇 번으로 죽일 수 있고, 오신고 한 번에 멀쩡한 프로젝트가 사라진다.

신고는 **관리자 큐에 쌓이고, 사유별 심각도는 알림 세기와 정렬 순서만 결정한다.** 숨김·삭제는 언제나 관리자의 수동 판단이다.

| 심각도 | 사유 | 처리 |
| --- | --- | --- |
| `CRITICAL` | 악성코드 · 개인정보 수집 · 사칭 | 관리자 즉시 알림 + 큐 최상단 |
| `HIGH` | 외부 상업 판매 · 저작권 · 부적절 · 추첨 조작 | 큐 상단 |
| `NORMAL` | 스팸 · 기타 | 일반 큐 |
| `INFO` | 링크 깨짐 | 관리자를 거치지 않고 제작자에게만 |

## 인증: 소셜 하나면 된다

|  | 일반 사용자 | 프로젝트 업로더 |
| --- | --- | --- |
| 할 수 있는 것 | 둘러보기 · 관심등록 · 설문응답 · 추첨응모 · 일정 · 신고 | + 프로젝트 등록/수정 · 일정 · 설문 · 추첨 개설 |
| 필요 인증 | Google / Kakao / Naver / GitHub **아무거나 하나** + 닉네임 · 이메일 확인 | 같음 |

GitHub 계정 연결은 **선택**이다. 연결하고 저장소 주소를 넣은 프로젝트에만 **소유 확인** 배지가 붙는다. 저장소를 요구하면 비공개 저장소로 만든 팀 프로젝트나 저장소가 없는 결과물이 통째로 빠지는데, 이 서비스가 모으려는 것은 코드가 아니라 **써볼 수 있는 결과물**이다.

### 등록에 필요한 것은 데모 주소다

| 필수 | 선택 |
| --- | --- |
| 이름 · 한 줄 소개 · **데모 주소** · 카테고리 · 소개 | GitHub 저장소 · 태그 · 아이콘 · 스크린샷 |

`둘러본다 → 써본다 → 익명으로 피드백을 남긴다` 가 이 서비스의 전부다. 써볼 곳이 없으면 나머지가 성립하지 않으므로 데모가 필수 자리에 온다. 저장소를 넣으면 스타·언어·README 를 함께 가져온다. 아이콘을 비워두면 프로젝트 이름 첫 글자로 만들어 쓴다.

### 닉네임은 자기소개가 아니라 소속 표기다

가입한 사람은 예외 없이 **`기수_지역_반_이름`** 형식의 닉네임을 갖는다. `16_구미_1반_김싸피` 처럼.

|  | 받는 값 |
| --- | --- |
| 기수 | 숫자 1~50 |
| 지역 | 서울 · 대전 · 광주 · 구미 · 부울경 (SSAFY 캠퍼스) |
| 반 | 숫자 + `반` |
| 이름 | 한글 2~10자 |

프로젝트를 올린 사람과 일정을 적은 사람이 누구인지 한 줄로 드러나야 하고, 같은 반끼리 서로를 찾을 수 있어야 한다. "김싸피" 만으로는 그게 안 되고 동명이인을 구별할 방법도 없다.

**소셜 로그인만 있어서 가입 폼이 없다.** 프로바이더가 준 이름(`김싸피`, `kdpark`)이 그대로 들어오므로, 첫 로그인 뒤 `/nickname` 을 한 번 세워 여기서 받는다. 형식을 갖추지 못한 사람은 로그인·이메일 확인·정책 문서를 빼고 어디로 가든 이 화면으로 돌아온다. 이미 가입한 사람도 같은 길을 지나므로 결국 전원이 같은 형식이 된다.

지역은 목록으로, 기수·반은 숫자로 받는다. "형식에 맞게 적어주세요" 라고 안내하고 자유 입력을 받으면 밑줄을 빠뜨리거나 지역을 제멋대로 적는 실패가 계속 나온다. 그래도 **서버는 다시 검사한다** — 화면 게이트는 레이아웃이 걸지만 Server Action 은 라우트를 거치지 않고 직접 호출될 수 있어서, 실제 방어는 `requireNamedViewer` 가 한다.

이 규칙은 **SSAFY 재직/재학자를 전제로 한다.** 외부에서 오신 분은 그대로 쓸 수 없다 — 원래 소속 입력은 선택이었지만, 닉네임을 소속 표기로 못박으면서 사실상 필수가 됐다.

**다만 이 형식 검사는 인증이 아니다.** 소속을 본인이 적어내는 방식이라, 형식만 맞추면 실제 구성원이 아니어도 통과한다. 다중 계정도 걸러내지 못한다. 형식 검사가 하는 일은 억제이지 확인이 아니다.

실제 확인은 **Mattermost 계정 연결**이 한다(위 5번). 싸피가 이미 확인한 계정을 서버가 다시 확인해 붙이고, 한 Mattermost 계정은 한 firework 계정에만 붙는다. 경품 추첨을 계속 운영한다면 이 구분이 특히 필요하다 — 응모권이 걸린 곳에서는 "적어낸 소속"과 "확인된 계정"의 차이가 그대로 비용이 된다.

**이메일 확인은 게이트가 아니다.** 설문 응답(=추첨 응모)과 프로젝트 등록을 막는 것은 닉네임뿐이다.

원래는 여기에 이메일 확인을 함께 걸었다. 계정을 여러 개 만들면 추첨 응모권이 그만큼 늘어나기 때문이다. 그런데 닉네임이 `기수_지역_반_이름` 이 되면서 계정 하나를 더 만들려면 실명과 소속을 그만큼 더 써내야 한다. 같은 반 사람들이 보는 화면에서 그건 이메일 인증보다 강한 억제다. 반대로 이메일 확인은 **이메일을 주지 않는 프로바이더를 통째로 막았다** — 카카오는 비즈 앱으로 전환해야 이메일 동의항목이 열린다.

확인 자체는 남아 있다(오른쪽 위 메뉴 → 이메일 확인). **관리자 승격은 여전히 검증된 이메일에만 적용된다** — 이메일은 프로바이더가 알려주는 값이라, 프로바이더를 믿을 수 있을 때만 관리자를 맡길 근거가 된다.

**카카오에는 이메일을 아예 요청하지 않는다.** 이메일 동의항목은 비즈 앱으로 전환해야 열리는데, 열리지 않은 앱에서 요청하면 동의 화면이 아니라 오류로 끝난다. 닉네임·프로필 사진만 받고, 이메일 자리에는 회원번호로 자리표시자를 만든다(`kakao-{id}@no-email.invalid`). 계정의 기본키 노릇을 하는 `email` 이 비어 있으면 계정 생성 자체가 실패하기 때문이다. 같은 사람은 늘 같은 값이 나오므로 재로그인해도 계정이 갈라지지 않고, 실제 주소가 아님이 도메인에 드러난다. 이 계정은 `emailVerified` 가 false 로 남아 관리자가 될 수 없다.

**관리자**는 `ADMIN_EMAILS` 환경변수로 처음 한 명을 만들고(배포 직후엔 관리자가 없어 신고 큐를 열 사람이 없다), 그 뒤로는 `/admin/users`에서 서로 임명한다. 이메일은 소셜 프로바이더가 알려주는 값이라, 계정 연결과 같은 기준으로 **이메일이 검증된 계정에만** 승격이 적용된다. 본인 해임과 마지막 관리자 해임은 막혀 있다.

### 버전을 고정한 이유 (그냥 최신으로 올리면 깨진다)

- **TypeScript는 6.0.3에서 멈춘다.** 7.0은 Go 네이티브 재작성이라 `lib/typescript.js`가 빠졌고, Next.js가 TypeScript를 인식하지 못한다. `typescript-eslint@8.69.0`의 peer 범위도 `>=4.8.4 <6.1.0`이라 7은 아예 밖이다. 프로그래매틱 API는 7.1 예정.
- **ESLint는 9.39.5에서 멈춘다.** `eslint-config-next`가 끌어오는 `eslint-plugin-react@7.37.5`의 peer가 `^9.7`에서 끊긴다. ESLint 10에서는 제거된 `context.getFilename`을 써서 실행 즉시 터진다.
- **Prisma는 7.10.0을 정확히 지정한다.** `prisma@latest`는 `8.0.0-rc`를 끌어온다.
- Prisma 7부터 연결 문자열이 `schema.prisma`가 아니라 `prisma.config.ts`에 있고, 런타임은 드라이버 어댑터(`@prisma/adapter-pg`)로 연결한다. `.env` 자동 로딩도 사라져서 설정 파일에서 직접 읽는다.

## 시작하기

```bash
git clone https://github.com/park-rudxo/firework.git
cd firework

npm run setup                               # 1) .env 를 만들고 비밀키를 채운다
npm run db:up                               # 2) PostgreSQL 18 — 준비될 때까지 기다린다
npm ci                                      # 3) npm install 이 아니라 ci
npm run db:deploy                           # 4) 스키마 적용
npm run db:seed                             # 5) 데모 데이터 (선택이지만 권장)
npm run dev
```

http://localhost:3000 을 열면 프로젝트 6개가 들어있는 상태로 뜬다.

**볼륨 경로가 남아 있어 컨테이너가 안 뜨면** 볼륨을 지우고 다시 만든다. `postgres:18`
부터 데이터 경로가 바뀌어서(`/var/lib/postgresql/data` → `/var/lib/postgresql`),
예전 설정으로 만들어진 볼륨이 남아 있으면 기동에 실패한다.

```bash
docker compose down -v      # 볼륨까지 지운다 (개발용이라 안전)
npm run db:up
npm run db:deploy && npm run db:seed
```

`docker compose up -d` 는 컨테이너를 띄우기만 하고 **준비될 때까지 기다리지 않는다.**
첫 실행은 Postgres 가 데이터 디렉터리를 초기화하느라 몇 초 걸리는데, 그 사이에
`db:deploy` 를 돌리면 연결이 거절된다. `npm run db:up` 은 `--wait` 로 healthcheck 가
통과할 때까지 기다린 뒤 반환한다.

**안 뜨면 `npm run doctor`.** 연결 문자열이 실제로 어디를 가리키는지, 그 데이터베이스에
테이블이 있는지, 시드가 들어갔는지를 확인해서 다음에 칠 명령을 알려준다.

`npm run setup` 은 node 내장 모듈만 쓰므로 `npm ci` 전에도 돌아간다. 이미 있는 `.env`
는 건드리지 않고, 비밀키가 이미 채워져 있으면 덮어쓰지 않는다.

**순서가 중요하다.** `npm ci` 의 `postinstall` 이 `prisma generate` 를 부르고, 그게
`DATABASE_URL` 을 읽는다. `.env` 가 없으면 설치가 거기서 실패한다.

**`npm install` 말고 `npm ci`** 를 쓴다. `npm install` 은 의존성 트리를 다시 풀면서
npm 10 의 arborist 버그(`Cannot read properties of null (reading 'edgesOut')`)를 밟을 수
있다. `npm ci` 는 락파일을 그대로 설치하므로 그 경로를 타지 않는다.

### 로그인 없이 볼 수 있는 것

소셜 로그인을 하나도 설정하지 않아도 **홈·둘러보기·프로젝트 상세·일정·정책 문서**는
그대로 열린다. 시드 데이터가 들어있으면 큐레이션 섹션도 채워진다.

설문 응답·추첨 응모·프로젝트 등록처럼 로그인이 필요한 화면을 보려면 소셜 프로바이더를
최소 하나 설정해야 한다. 가장 빠른 건 GitHub 이다(업로더 인증에도 어차피 필요하다).

1. https://github.com/settings/developers → **New OAuth App**
2. Homepage URL `http://localhost:3000`
3. Authorization callback URL `http://localhost:3000/api/auth/callback/github`
4. 발급된 Client ID / Secret 을 `.env` 의 `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` 에 넣는다

다른 프로바이더의 콜백 URL도 형태는 같다 — `{BETTER_AUTH_URL}/api/auth/callback/{provider}`.

`ADMIN_EMAILS` 에 적힌 이메일로 로그인하면 관리자가 된다. 단 **이메일이 검증된 계정**
(Google·GitHub)이어야 승격된다. 비워두면 신고 큐를 열 수 있는 사람이 아무도 없다.

`GITHUB_TOKEN`(public repo 읽기 전용 PAT)이 없으면 저장소 메타 수집이 시간당 60회로
제한된다. 있으면 5,000회.

### 명령어

```bash
npm run dev          # 개발 서버
npm run build        # 프로덕션 빌드
npm run lint         # ESLint
npm run typecheck    # tsc --noEmit
npm test             # Vitest — 익명성·구독 동의·권한·발송 규칙 (DB 가 떠 있어야 한다)
npm run e2e          # Playwright — 공개 화면 흐름 (DB 에 시드가 필요하다)
npm run setup        # .env 생성 + 비밀키 채우기
npm run doctor       # 왜 안 뜨는지 진단
npm run deploy:check # 배포 직전 환경변수 점검
npm run db:up        # PostgreSQL 을 띄우고 준비될 때까지 대기
npm run db:migrate   # 마이그레이션 생성·적용
npm run db:seed      # 개발용 시드 데이터
npm run db:studio    # Prisma Studio
```

`npm test` 는 두 종류를 함께 돌린다. `tests/*.test.ts` 는 순수 함수와 스키마만 보므로 DB 없이 돌지만,
`tests/db/*.test.ts` 는 **진짜 Postgres 를 쓴다** — "구독을 끊으면 알림 동의도 지워지는가" 같은 규칙은
여러 테이블에 걸쳐 있어 함수를 흉내내는 것으로는 확인할 수 없기 때문이다.
그래서 `npm run db:up && npm run db:deploy` 를 먼저 해두어야 한다.
이 테스트들은 테이블을 비우고 시작하므로 **개발용 데이터가 지워진다** — 확인하고 싶은 시드가 있다면
`npm run db:seed` 로 다시 채우면 된다.

E2E 는 시드가 들어간 DB 를 전제로 한다. 브라우저가 이미 깔린 환경(CI 러너, 샌드박스)에서는
`PLAYWRIGHT_CHROMIUM_PATH` 로 실행 파일 경로를 넘기면 새로 내려받지 않는다.

### 배포

Vercel + Neon 기준 단계별 절차는 [`docs/DEPLOY.md`](docs/DEPLOY.md) 에 있다.
올리기 전에 `npm run deploy:check` 로 콜백 URL·자격증명·관리자 설정을 먼저 확인한다 —
여기서 잡히는 것들은 대부분 배포 후에 사용자가 먼저 밟아야 드러나는 종류다.

로그인 뒤의 흐름(설문 제출, 추첨 실행)은 소셜 OAuth 가 필요해 E2E 로 재현하지 않는다.
그쪽은 순수 함수 단위 테스트와 스키마 검사로 덮는다 — 추첨은 부수효과 없는 함수라 결정성을
직접 검증할 수 있고, 익명성은 스키마 형태 자체를 단언한다.

## 구조

```
src/
├─ app/                  라우트. API 라우트는 Better Auth 캐치올과 Mattermost OAuth
│                        콜백뿐이고, 나머지 쓰기는 전부 Server Actions + Zod 검증
├─ components/           UI
├─ features/             도메인 로직
│   ├─ project/          등록·수정·권한(permissions.ts)·소유 확인(ownership.ts)
│   ├─ subscription/     구독과 알림 동의. 규칙은 mutations.ts 에 모여 있다
│   ├─ notification/     사이트 알림 발행과 발송 큐 적재(dispatch.ts)
│   ├─ mattermost/       계정 연결·웹훅 검증·발송 직전 동의 확인(deliver.ts)
│   ├─ bug/              버그 제보와 처리 상태
│   ├─ update/           진행 소식
│   └─ curation · calendar · survey · raffle · report
└─ lib/                  auth · db · github · sanitize · session · env · secret-box
prisma/schema.prisma     데이터 모델
tests/db/                진짜 Postgres 에 대고 도는 테스트 (구독·발송·권한)
```

`src/lib/sanitize.ts`가 특히 중요하다. 이 서비스가 화면에 얹는 HTML은 상당수가 **남의 GitHub 저장소 README**다. 신뢰 불가 입력으로 취급해 사용자 마크다운과 같은 파이프라인을 통과시키고, `next.config.ts`의 CSP로 한 겹 더 막는다.
